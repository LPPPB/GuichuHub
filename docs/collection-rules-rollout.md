# 官方鬼畜榜与独立潜力榜发布清单

本分支只完成代码与本地验证；没有部署、修改线上模式、回写历史或迁移数据库。所有数据库测试使用夹具自建的临时 PostgreSQL。默认 `COLLECTION_RULES_MODE=shadow`，API 和 Worker 必须使用相同值。

## 三种模式与数据口径

| 模式 | 公开鬼畜榜 | 公开潜力榜 | 后台行为 |
| --- | --- | --- | --- |
| legacy | 原自定义规则 | 原潜力规则 | 停止独立官方刷新，保留已有新快照 |
| shadow | 原自定义规则 | 原潜力规则 | 同时生成新规则结果及旁路摘要 |
| official | B站 `ranking/v2?rid=1007&type=all` 原顺序前20 | 独立发现、真实统计严格筛选前30 | 独立官方刷新与完整发现分开执行 |

官方结果保存完整有效列表，展示名次沿用源列表位置；不按分区或本站分数重排。首页只展示前三项。官方请求失败、空榜或无效数据只记录尝试，保留同源上次成功快照；没有成功快照时明确不可用。抓取时间是本站收到响应的时间，不是官方榜单更新时间。超过60分钟显示过期，超过24小时显示历史榜单。

潜力榜保留独立发现。有效鬼畜分类、1500至100万播放、互动质量至少10、21天内且不晚于当前时间、完整真实核心统计是默认门槛。分数只用于同批候选的相对比较。未知指标不当零；未补全作品进入有上限的待补池。成功空榜可以替换旧榜，失败不行。历史统计和旧分数不追溯重算。

## 上线前只读核实

1. 核实实际主机、代码目录、Git远程/提交、Compose文件和服务名、Nginx/Caddy入口、当前API/Worker/前端镜像及摘要。不要从旧记录推断当前部署。
2. 记录现有模式、受影响服务镜像与上一版发布标识，保留可用的回滚镜像。配置只检查必要项，不输出Cookie、数据库URL、令牌或完整环境变量。
3. 核实最近备份的时间、清单及校验和，并在独立临时数据库验证可恢复。确认现有备份流程已成功；本次没有提供或执行覆盖生产数据的恢复操作。
4. 核实角色权限支持现有 `dashboard_state` 更新、元信息登记、观测写入和 PostgreSQL 会话 advisory lock。无schema变更；不运行DDL、自动迁移或downgrade。
5. 查看本分支最终提交、测试和独立审查结论；受控上游探测失败时，应在实际部署出口核实可用性，保持shadow，不绕过风控切换网络。

## 发布与shadow观察（取得部署授权后）

只发布受影响的API、Worker与前端。保留PostgreSQL、卷、SQLite、Cookie、密钥、环境文件、其他服务与入口配置。不要执行 `docker compose down -v`、批量覆盖目录、数据清理或环境文件覆盖。实际Compose命令应根据只读核实结果填写；本文不假定线上服务路径。

API/Worker同时使用 `shadow`。先验证健康，再观察至少连续24小时，且完整覆盖两个全量发现周期；默认每日03:00、15:00，只有时间满24小时但没有两个周期仍不满足条件。至少产生两个有效、不同批次的官方快照；检查失败回退和锁冲突。任一条件不足就延长观察，不自动切换。

| 检查 | 预期与失败处理 |
| --- | --- |
| API `/api/health/live`、`/api/health/ready` | HTTP200、数据库与Worker心跳正常；失败停止切换，先排查或回滚受影响服务 |
| Worker启动 | 到期官方预热在原全量startup之前；startup登记新BV但没有额外观测点 |
| 官方独立任务 | 默认北京时间每小时:05/:35；与完整/手动/轻量观测共用PG锁，忙碌最多延迟5分钟重试一次 |
| 请求预算 | 候选≤400、待补≤400、发现逻辑≤60、详情≤160、标签≤64、同接≤160；摘要分列实际HTTP尝试/缓存命中/跳过 |
| 旁路摘要 | `crawl_runs.stats`保留mode、rules_version、发现/旧榜/新榜数量、coverage、rejected、requests和耗时；检查异常空榜及来源偏斜 |
| 观测 | 可见官方20/潜力30优先，普通目标合并去重后≤200；雷达参考配额单列且不增加同接请求 |
| 历史 | 仅真实完整新统计产生观测；旧官方样本只登记元信息；模式切换不改已有历史 |

本机的只读源核验命令（输出为公开视频信息，不连接应用数据库，也不读取Cookie）：

```powershell
cd <已核实的代码目录>/backend
.venv/Scripts/python.exe scripts/verify_collection_source.py --output <独立临时目录>/official-source.json
```

一次逻辑探测最多两次HTTP，仅对网络/5xx重试；412、429或B站业务错误不重试。退出0表示保存响应的源顺序与采集结果一致；非零不表示可以切换。不要用另一时刻榜单要求完全相等。

## 人工切换与上线验证

shadow条件满足、备份与回滚点再次确认后，由用户确认切换范围，将API/Worker一起设为 `official` 并按已核实的部署方式更新。不能只更改一个进程。

1. HTTP检查Dashboard和独立榜单：`/api/dashboard`中的 `kichu_rank_meta.snapshot_id` 必须等于 `/api/kichu-rank` 的 `meta.snapshot_id`，BV顺序一致、source为 `bilibili_official_ranking_v2`、rid=1007、type=all。页面刷新或API换进程后仍一致。
2. 触发已有权限保护的手动刷新后，官方榜仍来自持久快照；潜力榜临时成功新快照可展示，TTL过期回到同规则持久快照，失败不填旧规则数据。
3. 实际浏览器检查390px和1440px：首页、鬼畜榜、潜力榜的来源/抓取时间、同BV不同名次、失败/过期状态、收藏、移动导航和趋势操作。HTTP200或资源哈希相等不能替代视觉检查。
4. 检查Worker下一次官方刷新、观测与完整发现的日志、锁释放及心跳。生产失败演练需单独明确范围；优先使用本地固定响应回归，不能为了演练修改生产Cookie或网络。

## 回滚

数据契约不变、旧内部字段保留，因此可以先将API/Worker同时恢复 `legacy`，验证旧榜恢复、健康和心跳正常。必要时将受影响服务恢复为上线前记录的镜像，前端一起回滚。不要删除新快照或历史记录，也不做数据库恢复覆盖或schema回退。不能证明安全时停止进一步变更，保留证据再处理。

## 本地验收

- 后端：完整pytest，临时PostgreSQL覆盖会话锁、原子发布、模式切换/失败/回滚、startup元信息和历史保护；手动联网脚本导入不产生HTTP。
- 前端：完整Vitest、生产构建、SEO校验、合成API浏览器布局（1920/1440/1280/900/390/320）。布局不会访问生产或使用凭据。
- Compose：以测试夹具合成配置渲染，API/Worker模式一致；无新增服务、卷、端口或数据库schema。
- 实时源核验的成功与否独立记录；它不能替代实际生产出口的shadow观察。
