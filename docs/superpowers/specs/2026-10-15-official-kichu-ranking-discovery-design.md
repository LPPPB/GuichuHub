# GuichuHub 官方鬼畜榜与独立潜力发现改造设计

日期：2026-10-15（Asia/Shanghai）

状态：用户于 2026-10-15 阅读书面规格交付后回复“继续”，本规格评审通过。实施计划另行交付评审，尚未修改产品代码或部署。

## 1. 用户意图与成功标准

旧采集规则建立在鬼畜分区排行榜不可用的假设上。现已实测新版榜单可用，需要恢复“鬼畜榜”的官方排名语义，同时保留 GuichuHub 主动发现新作品的能力。

用户明确选择：**鬼畜榜遵循官方排名，潜力榜保留独立发现与评分。** 用户随后同意以下范围：独立官方榜、独立发现池、共享统计补全、修正筛选和去重、独立刷新与可靠回退、旁路验证后切换。

成功标准：

- 同一份上游响应生成的鬼畜榜，其成员和名次与官方返回顺序一致，不受播放量、本地评分或旧分区白名单重排。
- 未进入官方榜的鬼畜作品仍可从独立来源进入潜力榜；低播放作品不再因发现阶段的播放 Top30 截断而提前出局。
- 正式潜力榜只采用完整真实核心统计，通过明确门槛后评分；不足时如实展示较少作品。
- 网络失败、异常响应、空榜和缓存回退均能说明来源与时间，不把旧自定义榜标成官方榜。
- 保留既有 UI 布局、服务架构和历史数据，采集请求有预算，发布可以回滚。

本次不重写评分公式、不承诺跨期分数可比、不新增历史名次产品、不扩展到全站推荐系统；不重构 UP/日历任务，不引入 Redis、Celery 或新服务。

## 3. 方案选择与组件边界

采用“拆分官方榜与独立发现，修正共享链路”。只改 `rid` 会保留旧过滤、播放重排、缓存混源等问题；全面重写采集平台会扩大风险，目前没有证据支持。

| 组件 | 输入 | 输出与职责 |
| --- | --- | --- |
| 官方榜采集器 | 固定榜源身份和受控请求 | 保序榜单、榜单身份、响应校验和采集结果；不做潜力筛选 |
| 多源发现器 | 热门、搜索、经验证的新投稿、种子词、官方榜候选 | 合并来源的候选池；不提前按播放量取 Top30 |
| 共享补全器 | 待补全候选和本轮已取得的真实统计 | 有来源和时间的指标；详情、标签、同接分别预算和去重 |
| 潜力生成器 | 分类已验证、核心统计完整的候选 | 严格筛选后独立评分、排序，最多展示 30 条 |
| 派生内容生成器 | 明确限额的鬼畜发现样本、音乐/搞笑素材等 | 热梗、BGM、弹幕、评论，不直接继承官方 100 条采集规模 |
| 快照发布与读取器 | 采集结果、最后成功快照、运行模式 | 原子发布、失败状态、统一 API 投影和展示来源 |

复用现有 Worker、调度器、PostgreSQL 与仓储权限。新增官方榜任务仅在 Worker 执行，API 只读官方快照，不增加 API 的采集写入权限。既有手动全量刷新执行路径不在本次改造成新队列。

## 4. 官方榜语义与分类

榜源身份固定为 `source=bilibili_official_ranking_v2`、`rid=1007`、`type=all`。使用现有 HTTP 客户端和网络配置，不添加 Cookie、代理或凭证绕过机制。

- `official_rank` 为上游数组从 1 开始的位置。不得按 `views`、`potential_score`、`score`、`now_rank` 重排。
- 保存完整、经过结构校验的源列表；公共页面维持最多 20 条，首页维持前三条。第一阶段不新增分页或“全 100 条”交互。
- 不应用潜力门槛、搜索一年时效或旧分类白名单。可选展示字段缺失时使用空值/现有占位，不删除可识别的榜单成员。
- 无法识别 BVID 的条目不展示，保留其原始位置和异常摘要，其后的名次不重新编号。重复 BVID 保留首次位置，记录重复位置。
- 源列表不强制等于 100 条。非空响应中有效唯一条目低于源条目的 90%，或前 20 个位置有无法识别/重复的 BVID，整份响应视为结构异常，不替换最后成功榜。其他局部异常可以发布，并标记 `partial=true` 和缺失位置。
- `tid/tname` 原样保留为旧分类；新分类放入 `category_v2`，保留原始 ID 和名称。不能把 `tid` 统一改为 1007，也不能伪装成某个旧鬼畜子分区来通过 SQL 过滤。
- 官方榜源决定榜单成员身份；分类异常仅记录，不擅自替官方删榜。

潜力分类采用另一条明确规则：新父分区优先，`pid_v2=1007` 可确认鬼畜，明确为其他新父分区时不能由旧 `tid` 或子分区放行。新父分区缺失时才查询已核验的子分区映射，首版仅采用本次响应实证的 `{2063:1007}`；其他子分区仅凭未验证 ID 不能放行，先补详情。新分类字段完全缺失时才使用现有旧分区白名单；新分类存在但无法确认则待补全。官方上榜本身不绕过潜力分类规则，后续扩充映射必须附上游响应证据与测试。

新分类首先保存在当前快照和候选 JSON 中。本期不新增 `videos` 分类列，也不回填历史数据。依赖旧 `videos.tid` 的爆发榜、雷达参考 SQL 保持原口径：新分类作品可能缺少对应雷达画像，按现有不可用语义展示，不补零、不改官方名次，也不宣称这些历史分析已支持新版全分类。

## 5. 快照、状态与时间契约

使用既有 `dashboard_state.payload` JSONB，新增两个独立的官方榜字段；新版潜力快照、尝试和待补集合也使用该 JSONB，具体见第 6 节。无需 DDL 或 Alembic revision。

### 5.1 最后成功快照 `official_kichu_snapshot`

| 字段 | 含义 |
| --- | --- |
| `schema_version` | 当前契约为 1 |
| `snapshot_id` | 成功响应的 UUID；同一发布事务及重试提交复用，不以内容哈希冒充上游批次 |
| `source/rid/type` | 上述固定身份 |
| `fetched_at` | 本站成功接收并校验响应的 Unix 秒；不是官方更新时间 |
| `upstream_updated_at` | 上游未提供可靠时间时为 `null` |
| `source_count/item_count` | 原始条目数、有效唯一条目数 |
| `display_limit` | 默认 20 |
| `partial/anomalies` | 局部异常标志及数量、位置等摘要 |
| `items` | 完整保序条目；每条含兼容视频字段与 `official_rank` |

榜单身份属于快照，不能用累计 `videos.source` 证明某条历史榜的权威来源。完整真实核心统计沿用 `metrics_source=bilibili_stat` 兼容既有雷达契约，另在 JSON 中保留 `metrics_endpoint`（`ranking_v2/view/popular`）及实际 `observed_at`，缺失统计标为未知。指标来源和榜单来源分别记录，避免“官方榜成员”被理解成所有本地补全指标都来自榜单接口。

### 5.2 最近尝试 `official_kichu_attempt`

保存 `attempt_id`、`started_at`、`finished_at`、`outcome`、稳定错误分类、请求次数和异常摘要，不保存响应凭证、请求头或完整堆栈。`outcome` 为 `success/empty/error/invalid/skipped`。

成功后在一个 dashboard 行锁事务中一起提交完整快照和成功尝试。失败/空榜/结构异常只更新最近尝试，不改动最后成功快照的内容、编号和成功时间。失败状态更新不得推进全局“内容已更新”时间；数据库状态版本可以推进，使各 API 进程读到失败状态。

| 本轮结果 | 已有同源官方快照 | 无官方快照 |
| --- | --- | --- |
| 合法非空 | 原子替换，状态 `available` | 首次发布，状态 `available` |
| 合法结构但空列表 | 保留旧榜，`last_attempt.outcome=empty` | `data=[]`，状态 `unavailable` |
| 网络/风控/结构失败 | 保留旧榜，记录错误 | `data=[]`，状态 `unavailable` |
| 任务忙或未到刷新时间 | 保持现有快照和成功时间 | 仍为 `unavailable` |

该接口未提供可靠“当前确实没有榜单”的信号，因此成功空列表视为单独的异常空榜，不清空榜单。这与网络错误有不同错误分类和计数。若上游未来增加可信空榜信号，需另行修改契约并覆盖测试。

最后成功时间超过 60 分钟即 `stale=true`；最近一次刷新失败但尚未超过时限时，显示更新失败状态，不假称成功。旧官方快照不自动删除：超过 24 小时显示明确的历史榜提示，继续提供原成功时间；新成功响应到来后恢复。没有来源信息的存量榜只标为 `legacy_custom`，不得成为官方回退快照。

并发提交按尝试的开始时间判断新旧：较早尝试的迟到结果不能覆盖较新尝试状态；较早成功快照不能覆盖较新成功快照。失败不妨碍晚到、但比当前成功快照更新的合法成功结果独立提交。

### 5.3 与旧状态兼容

内部旧 `kichu_rank` 保留为旧自定义榜投影，供旁路比较及代码回滚；发现池中单独生成其播放 Top30/展示 Top20，不再用该截断后的列表作为新版潜力池。内部旧 `hot_videos` 同样保留旧规则结果，供旁路展示和回滚；新版潜力结果及元信息单独存为 `potential_v2_snapshot`。两套规则共用本轮请求结果，但使用不同对象副本，不能彼此覆盖分数或筛选状态。新增官方字段只允许专用快照仓储更新，普通全量抓取和实时缓存合并不得覆盖它们。

官方模式下，公共 `kichu_rank` 是统一读取器从 `official_kichu_snapshot.items` 生成的前 20 条投影，不是直接读取内部旧 `kichu_rank`。这种适配避免双写列表和元信息时出现混源。

## 6. 独立发现、补全与潜力筛选

### 6.1 发现与采样

保留独立热门、关键词搜索和验证可用的新投稿入口。关键词搜索同时覆盖按最新投稿和现有综合排序；官方榜可以贡献候选，但没有覆盖其他来源的优先权。

每轮共享热门页响应，分类器在同一份数据上各自筛选，不为音乐、搞笑和全站热门重复请求相同页。音乐/搞笑继续服务素材和派生内容；只有经过明确鬼畜分类验证的作品才能进入鬼畜潜力池。

跨来源按 BVID 合并 `sources`，不再“首条保留、其余丢弃”。一个来源不符合年龄或分类条件，不得提前把 BVID 标记为全局排除。原始来源记录与最终分类结论分开。

首版预算为设计默认值，在配置中集中定义并进行范围校验，发布时核验实际生效值：

| 项目 | 单轮上限与选择规则 |
| --- | --- |
| 热门 | 15 页，每页沿用现有限额；全轮共享 |
| 鬼畜关键词 | 沿用 4 组关键词/分区，每组按最新投稿和现有综合排序各最多 2 页，共 16 次搜索 |
| 音乐/搞笑搜索 | 各自最多 7 页，沿用现有关键词范围 |
| 种子词搜索 | 全部种子合计最多 8 页，按轮换次序覆盖，不能随词数无限增长 |
| 全站榜、新投稿 | 各最多 1 次逻辑请求；新投稿沿用已验证入口，不直接替换为 1007 |
| 发现请求总闸 | 最多 60 次逻辑请求；各来源仍须服从其更低上限 |
| 潜力候选 | 最多 400 个唯一 BV：官方 100、最新搜索 100、综合搜索 100、新投稿 20、热门等 80；不足配额由其他来源轮询补足 |
| 详情 | 每轮最多 160 个唯一 BV，已有完整真实统计的不再补抓 |
| 标签 | 每轮最多 64 个唯一 BV，只用于确有需要的派生样本，不在截断前全量抓取 |
| 潜力同接 | 每轮最多 160 个唯一 BV，仅对真实统计筛选合格者发起，遵守现有熔断和节流 |

以上是请求上界与公平采样规则，不是采集覆盖率保证。来源内以发布时间优先，时间相同时按 BVID 稳定排序；跨来源轮询，不按累计播放统一争抢配额。共同候选计一次总量，保留所有来源。详情预算先为尚无真实统计的新投稿和最新搜索各保留最多 20 个名额，其他待补候选轮询领取，未用名额回流。

预算外或补全失败的候选进入有界的 `potential_pending` 当前状态，最多 400 条，保留来源、首次发现和上次尝试时间，供下一轮在其来源配额内优先重试；不存估算分数，不把它们当正式榜。过 21 天的待补候选退出当前待补集合，不删除 `videos` 或观测历史。持续失败项每轮最多尝试一次，不阻塞其他候选。

候选合并不拼接不同时点的指标来伪造完整真实统计。选择最新且完整的核心统计组，记录它的来源和采样时间；只有不完整结果时保留缺失状态。复用官方快照时，其统计获取时间距本轮评估时间不得超过 30 分钟，过期则在详情预算内更新或列入待补，不能将旧快照换成本轮时间。详情、标签和同接使用独立的每轮请求缓存，同一 BV/CID 成功或失败都不会在同轮被不同板块反复请求。

### 6.2 真实指标与硬门槛

完整核心统计要求 `view/like/coin/favorite/share/reply/danmaku` 全部存在、可解析且非负；真实零值有效，缺失值不能补成零或按播放比例估算。

潜力流程：

1. 按分类、可验证发布时间和来源配额构建候选；发布时间未知先补全，不当成零日期直接入榜。
2. 复用本轮官方/热门接口已有的完整统计，对缺失者在预算内抓详情。
3. 以最终真实数据执行分类、播放、年龄、互动硬门槛，补全后的播放超上限或互动不达标必须淘汰。
4. 对合格候选获取预算内同接，保留 `None ≠ 0`、历史平滑与风控熔断语义。
5. 仅对最终合格候选独立评分、排序，最多展示 30 条；并列分数以发布时间较新、BVID 稳定排序破同分。

首版门槛保留配置：播放量闭区间 `[1500,1000000]`、互动质量分至少 10、发布时间不晚于本轮时间且不早于 21 天。缺少发布时间或发布时间在未来的不正式入榜。不足 10 条也不自动把互动阈值降到 5/3/0，不把龄期延长到 30 天。

评分保持现有权重和批内 Min-Max。官方成员只有通过相同潜力门槛才参与本批归一，单纯上榜或超播放上限的官方作品不能扩张归一参照。现有 `extra` 外推可保留用于明确标记的辅助展示，但不参与潜力排名、候选统计或归一边界。

每批在 `potential_v2_snapshot` 中保存 `items` 和 `meta`，对外分别投影为 `hot_videos` 与 `potential_meta`；元信息包含 `rules_version=strict-real-stats-v1`、现有算法版本标识、批次时间、实际门槛、候选/合格/待补数量及来源覆盖。分数只解释为本批相对值；历史分数不重算，不能直接比较新旧批次分数高低来宣称效果提升。

新版潜力榜与元信息作为 `potential_v2_snapshot` 整体发布。流程正常完成但无人合格时发布空榜和本批元信息，不能由旧的真值合并逻辑保留旧名单。所有可用发现源失败、数据库故障或流程异常时保留最后成功榜及其时间；可写状态时在 `potential_v2_attempt` 单独记录最近尝试结果，数据库不可写时只记录失败日志，不声称失败状态已落库。尝试字段复用官方尝试的 ID、开始/结束时间、结果和安全错误摘要契约。部分来源失败而仍完成有效候选评估时允许发布，标记 `partial` 和缺失来源。旧内部 `hot_videos` 的生成规则只在过渡期保留，不能被当成新版空榜或失败时的自动填充。

## 7. 派生板块与观测历史

保留旧鬼畜发现样本的播放 Top30 作为派生输入，而非直接用官方 100 替换所有 `kichu_videos` 使用点。

| 板块 | 首版输入边界 |
| --- | --- |
| 热梗 | 原鬼畜发现样本 + 音乐/搞笑/热门；聚合前按 BV 合并，每个 BV 对同一关键词只贡献一次作品数和播放量 |
| BGM | 原音乐样本 + 鬼畜发现样本，先按 BV 去重，不自动增加官方全榜 |
| 弹幕 | 鬼畜发现前 20 + 潜力前 30 + 素材前 20，按 BV 去重，维持现有数量边界 |
| 神评论 | 鬼畜发现前 10，不跟随官方刷新每半小时重抓 |
| 音乐/搞笑素材 | 保持独立素材筛选，不因不贡献鬼畜潜力而删除来源 |

官方快照中的全部有效 BVID，发布前须完成元信息登记；新视频没有历史观测不妨碍显示官方名次。使用现有 `ts=None` 无观测登记能力，保留旧 BVID 的 `first_seen`、观测分级和历史；新官方非展示作品默认 `warm`，不把全部 100 条自动提升为高频观测。任何登记失败都不发布新快照。

官方轻量刷新只登记元信息和榜单快照，不另造播放/同接观测点。启动预热也先登记、再发布，不写合成观测。观测任务继续负责实际时间序列，实际取得的统计携带独立 `observed_at`；历史平滑同接不重复写成本轮实测。

轻量观测以公共有效榜单前 20 和潜力前 30 为优先目标，再补充原有 hot/warm 目标。合并去重后普通目标总数不超过 `OBSERVE_HOT_LIMIT`（默认 200），不得“限额后再追加榜单”。新版模式配置要求该限额至少为 50，避免配置同时要求覆盖全部展示作品却不给足名额。雷达参考样本保留已有独立额度及不抓同接的规则，日志分别报告普通目标和参考目标，不能声称参考请求也已包含在 200 中。该限额与官方源列表长度无关。

## 8. 调度、重试与请求成本

新增官方轻量任务，Worker 每 30 分钟运行，默认北京时间每小时 `:05/:35`，避开整点/半点观测起点。启动时仅当没有快照或快照超过 30 分钟才尝试；全量发现任务读取当前官方快照作为可选候选，不重复启动官方网络抓取。

默认发现全量周期仍由现有 `CRAWL_HOURS` 决定，代码默认 03:00/15:00；实际生产参数在发布时核验。独立名次刷新不代表所有派生板块也每半小时更新。

官方任务与现有全量/观测共享采集互斥约束；任务实例数为 1，合并错过的调度，不堆积补跑。现有 `_crawl_lock` 为进程内锁，不能证明 API 手动刷新和 Worker 互斥，因此这些抓取入口统一使用同一个 PostgreSQL 会话级 advisory lock：以固定 64 位常量为键，不能使用进程随机的 Python `hash()`；在同一专用连接领取并在 `finally` 释放后归还连接，最终持久快照发布也使用该连接开启短事务，连接丢失时终止该轮发布，禁止换连接继续提交。手动临时结果发布前须确认该会话仍有效，失联则丢弃本轮结果。只读 API 不持有该锁，不扩大数据库权限，不新增锁表或长期事务。

锁忙时官方任务记录 `skipped_busy`，最多延迟 5 分钟重试一次；仍忙则等待下次周期。既有手动/全量/观测入口保留各自的忙碌、等待和跳过行为，但均以共享锁结果为准。不得因为等锁持有数据库事务或反复创建线程。现有 UP/日历队列的资源锁和执行流程不纳入这把采集锁，不扩大到无关任务。

单次官方逻辑抓取最多 2 次 HTTP 尝试；仅超时、连接失败及 5xx 在节流后重试一次。412/429、风控业务码（例如 -352）、认证失效不紧密重试，不切换凭证或网络出口。新任务不再叠加现有全量任务级重试，正常周期再试。请求超时沿用现有受控客户端值。

发现/补全请求复用现有超时、节流、重试和熔断配置；日志同时计逻辑调用、实际 HTTP 尝试、去重命中、跳过和耗时，不能把上述逻辑预算当作包含重试的网络次数。整轮全量任务重试仍受现有 `RETRY_MAX_ATTEMPTS` 限制，重试轮次单独计数和批次身份。

当前代码可证基础发现上界约 51 次逻辑请求，另有标签、详情、同接、种子词、弹幕及评论。新官方榜本身只需 1 次逻辑请求，但不能宣称整个系统降到 1 次。比较请求成本必须包含实际启用来源、补全与重试，不通过提高频率掩盖单轮成本。

## 9. API、缓存与最小 UI 兼容

统一纯读取器选择当前模式下的有效榜单，Dashboard、`/api/kichu-rank`、观测目标选择都调用它。雷达装饰只附加字段，不改顺序，不就地污染持久快照。

- `/api/dashboard.data.kichu_rank` 继续是数组，新增并列 `kichu_rank_meta`；显式字段白名单必须透传元信息。
- `/api/kichu-rank.data` 继续是数组，新增顶层 `meta`；不把旧数组改成对象。
- 公共榜单默认只投影前 20，`meta` 包含完整源数量、展示数量、快照编号、来源、成功时间、最近尝试、状态与过期标志。
- 官方模式没有有效快照时，HTTP 接口仍可正常返回结构，但榜单为 `[]`、`meta.status=unavailable`；不能靠旧榜填满后称为官方。
- 现有实时刷新继续生成发现和派生板块的临时结果，官方榜始终从持久快照读取；手动刷新不在 API 进程新增官方采集。实时缓存失效、API 换进程或另一个 Worker 发布新榜后，两个接口仍选择同一最新快照。
- Dashboard 全局 `is_live/last_updated` 保留兼容，但官方榜时间以 `kichu_rank_meta.fetched_at` 为准。缓存键纳入官方快照/状态版本和按分钟变化的过期判断，不能因临时缓存未过期而遮住较新的官方榜。
- `hot_videos` 仍为数组，透传并列 `potential_meta`，实时候选与元信息也作为整体选择，不混用不同批次。新版模式可选择更新且成功的临时 `potential_v2_snapshot`，失败或过期则回退持久新版快照，没有新版快照时明确不可用，不暗用旧潜力名单。

UI 只做语义必要改动：鬼畜榜显示“哔哩哔哩官方榜”、本站抓取时间与失败/历史状态；潜力榜保留独立评分含义，不改导航、卡片布局和响应式行为。

官方名次由榜单上下文传入卡片，例如显式 `displayRank`；潜力卡片用自己的排序位置。不得全局采用 `video.official_rank ?? index + 1`，避免同一作品进入两个榜后串用名次。搜索、收藏等非官方上下文也不继承官方排名。局部异常保留名次空档，前三名样式按实际官方名次决定。

旧分类和新分类并存时，卡片优先展示已核验的新分类名称，来源异常不改变榜单成员。雷达历史不足沿用现有不可用展示，不更改算法参考池来强行生成画像。

## 10. 运行模式、旁路比较与回滚

增加集中配置 `COLLECTION_RULES_MODE`，取值 `legacy/shadow/official`，默认 `shadow`；未知值启动报配置错误，不静默回退。该开关控制本次成套规则的公共投影，`official` 同时启用官方鬼畜榜和严格真实统计潜力榜，两个榜仍保持独立采集和评分语义。已有生产配置文件不在本轮修改，API 与 Worker 生效模式必须在发布验证时一致。

| 模式 | 抓取及公共展示 |
| --- | --- |
| `legacy` | 不启动新官方任务；公共鬼畜榜和潜力榜使用明确标识的旧规则结果 |
| `shadow` | Worker 抓取官方快照，发现轮次生成新版潜力快照；公共两榜仍显示旧规则结果，产出比较摘要 |
| `official` | 公共鬼畜榜读取官方快照、潜力榜读取独立新版快照；失败只回退各自同源同规则快照 |

旁路模式同时比较两类新结果，通过后才切换公共展示。新旧计算共享 HTTP 结果，不重复执行整套网络采集；所有新增请求都受本期预算约束。新版独立潜力发现不因官方榜失败自动关闭。模式切换不删除历史或快照。记录运行模式和规则版本，防止将旁路测试误报为线上已切换。旁路结果不得覆盖公开旧结果对应的分数观测；新版潜力分先保存在独立快照，切换后才按新版批次写入分数观测。

在固定样本和本地临时 PostgreSQL 完成验证后，生产旁路至少覆盖连续 24 小时和两个全量发现周期；这段时间是验收观察窗口，不是保证上游每次成功。切换前至少取得两个不同抓取时间的有效官方快照，完成失败回退验证，且无来源错标、跨接口不一致或历史写入异常。若风控导致证据不足，延长观察而不是降低验收标准。

比较摘要只包含候选来源覆盖、未上官方榜的新发现、门槛淘汰原因、有效统计占比、去重、实际请求次数/耗时和状态。批内相对分数不作为新旧优劣的直接证据。对同一保存响应验证顺序，不拿时间不同的两次在线榜单强行要求完全相同。

模式回滚到 `legacy` 是展示来源和潜力规则回退，必须明确显示自定义榜及旧规则身份。产品代码回滚使用预留旧提交/镜像；由于内部旧字段保持兼容且无 schema 变更，不应需要数据库 downgrade 或恢复覆盖。回滚前后都核验实际服务版本和榜单身份，不承诺仅切配置等同于全部故障已恢复。

## 11. 必须通过的验收

实施遵循“先失败测试 → 最小实现 → 测试通过 → 分阶段提交”，以下是结果标准，不代替下一阶段实施计划。

1. 官方参数准确；输入播放量和潜力分逆序的样本，输出仍保持官方顺序；旧分类不匹配和超过百万播放的作品仍在官方榜。
2. 100 条和不足 100 条合法榜均可处理；缺 BVID、重复、缺可选字段和超过异常阈值分别得到约定结果，不伪造连续名次。
3. 网络错误、风控、成功空榜、部分异常、无旧快照、旧自定义缓存分别覆盖；来源、快照编号、时间不能错配。
4. 行锁原子提交、迟到结果、失败状态更新不刷新内容成功时间；全量抓取/实时缓存不能覆盖专用官方字段；不同 API/Worker 进程争用同一采集锁，异常和连接中断后不会错误发布或遗留锁。
5. Dashboard、独立接口及观测选样对同一状态选择同一快照；实时 TTL、跨进程状态版本、时间过期和雷达装饰不会产生不同榜序或污染缓存。
6. 未上官方榜的独立发现作品能进潜力榜；旧播放 Top30 之外的合格作品能参与，不被累计播放抢光配额。
7. 新旧分类冲突、未知分类、类型转换、未来/缺失发布时间都有确定结果；不能把新榜 `rid` 当视频 `tid`。
8. 估算互动无法过正式门槛；过期官方统计必须补全或待补；详情使播放超过上限、互动低于阈值或分类改变时重新淘汰；真实零值与缺失值区分。
9. 不足 10 条不放宽门槛；正常无人合格可发布空潜力榜；整体失败保留旧榜及时间，部分来源失败有标识。
10. 候选与请求预算、来源配额、待补重试、同轮失败去重均有验证；同一 BV 不重复补详情/标签，不重复计热梗贡献。
11. 官方全榜不自动进入潜力归一参照；保留 `extra`、同接 `None`、真实零同接、熔断、历史平滑和缺失指标回归。
12. 新官方 BV 在 startup 发布后可以正常观测，既有 `first_seen`/分级/历史不变；轻量官方刷新不制造观测点，登记失败不发布。
13. 观测普通目标含展示榜且总量不越界，参考目标单独计数；官方 100 条不引发 100 次标签/评论/同接补抓。
14. 同一 BV 同时在官方榜和潜力榜时，分别显示正确名次；首页、榜单页、收藏和移动端保持现有布局。
15. 三种运行模式、首次切换与回滚输出明确来源；旧镜像需要的内部旧榜字段仍存在，不改历史观测。

单元/集成测试使用脱敏固定响应和临时数据库，不依赖实时排名。`test_kichu_rank.py`、`test_ranking.py` 含导入时联网脚本，不能将它们当作确定性回归测试，也不直接运行未经筛选的整库 pytest。现有播放排序/最多 30 条断言只保留在旧榜或派生采样契约，不约束独立候选池和官方榜。

完成针对性后端回归、临时 PostgreSQL 集成验证和前端测试/构建，再进行一次受控上游联网验证。页面验收覆盖 390px 和 1440px，并检查名次、来源、时间、失败提示，不做无关 UI 重设计。
