# 手动 UP 观测与日历任务执行边界修复设计

日期：2026-10-03（北京时间）

状态：用户于 2026-10-03 确认“按设计实施”；实施计划待审核，尚未修改产品代码或部署。

## 1. 目标与范围

修复网页“刷新动态”和网页触发日历回填时，采集在 API 进程中执行而导致数据库权限错误的问题。按钮仍然可用，管理员提交后由专用 Worker 执行；刷新、重启和多个 API 进程不能导致进度丢失或重复采集。

用户已确认的方向：持久化任务队列、Worker 唯一执行、数据库保存进度及互斥、明确成功/部分失败/失败、受控重试。本文将这些方向具体化，供实施前审核。

不更换采集供应商，不调整现有每日四次 UP 观测时间，不新增 Redis/Celery 等服务，不修改观察名单，不开放公网网站，不复制或展示 Cookie/Token。不修补旧失败任务的历史状态，不删除或重写既有观测批次。

## 3. 方案选择

采用 PostgreSQL 持久化 UP 分析任务，与现有日历队列共用存储与 Worker 基础设施，但保持两种业务任务独立。

不采用给 API 增加采集写权限：这会保留双执行入口、进程内互斥和重启丢进度的问题。不采用 API 调用服务器 shell 或 Worker HTTP 管理接口：会新增权限与进程耦合，且仍缺少持久化进度。

执行边界：管理员按钮 / 定时调度 → 提交 PostgreSQL 作业 → Worker 领取 → 采集 → 原子保存观测 → 记录最终结果。API 只校验、提交和查询；Worker 不依赖浏览器或本地 SSH 隧道保持运行。

## 4. UP 分析任务数据与互斥

新增 `app.up_analysis_jobs`，通过唯一的新 Alembic revision 创建。字段包含：任务 ID、状态、提交来源、名单快照、进度、结果摘要、错误摘要、创建/开始/更新时间/结束时间、执行者、租约截止时间、递增 fencing token、执行次数和批次时间。

状态为 `queued`、`running`、`finalizing`、`succeeded`、`partial`、`failed`。`finalizing` 表示核心观测已保存，正在提交关联日历任务，仍属于活动状态；成功/部分失败/失败才是终态。终态不可被旧执行者覆盖。任务 ID 使用 UUID，不再依赖截断 ID 或 API 内存字典。

- 提交事务在数据库中串行化对同一 UP 分析资源的访问，并以部分唯一索引保证同一时刻最多一个 queued/running/finalizing 作业。手动与定时提交复用该作业，不各自启动采集。
- 名单快照只包含提交时启用的 UP，执行不修改名单。空名单不创建空采集作业，保持现有友好错误。
- Worker 使用事务和行锁领取任务；租约 120 秒，独立心跳每 20 秒续约。网络调用不得阻塞续约。
- 租约过期时允许恢复中断作业并递增 fencing token。所有进度与结果写入都验证执行者和 token；旧执行者不能提交数据。任务最多领取 3 次，超过次数明确失败，不无限重试。
- 批次时间在首次领取时固定；恢复同一任务复用该时间并幂等写入，避免生成重复批次。网络调用中断允许重新采集，但不声称恰好执行一次。
- 所有任务历史保留。本次不增加自动清理或删除逻辑。

API 在新任务表上仅有 SELECT/INSERT；Worker 有领取、进度和终态更新所需权限。API 仍没有视频快照与日历结果表写权限。只以 migration 角色执行 DDL 和必要的新表授权。

## 5. 执行与结果一致性

`start_analysis` 转为持久化提交适配层，不启动线程；定时入口也使用同一提交逻辑。`worker_entrypoint.py` 显式启动 UP 分析消费者，且只启动一次。

Worker 复用现有采集和分析算法。采集完成后，在一个事务中保存 UP 观测、全部 6 类视频快照，并将任务推进到 `finalizing`，同时校验 fencing token。任一核心写入失败，整个新批次回滚，任务报告失败；既有历史批次不受影响。

日历属于后续任务：分析数据保存成功后只提交日历增量作业，记录关联作业 ID。不能将“日历已入队”标记为“日历已完成”。若日历提交失败，UP 观测数据保留，分析任务报告 `partial`，明确已保存和未完成的部分。

进程在核心保存后、日历提交前中断时，恢复流程从 `finalizing` 继续提交日历，不重复采集整批。日历关联去重使用分析任务 ID，防止恢复时重复创建同一后续任务。完成关联提交后才进入成功终态；提交失败则进入部分失败终态。

错误摘要只暴露稳定错误码和安全提示，不返回数据库 URL、SQL 参数、Cookie 或 Token。`done` 表示进入终态，不代表成功。

## 6. 日历执行边界与重试

`enqueue_calendar_job` 只入队，移除隐式调用 `ensure_calendar_worker`。专用 Worker 的入口是唯一允许启动日历消费者的位置；冷启动、网页提交、UP 审核新增和定时提交均需覆盖测试。

日历去重继续复用 queued/running 作业；时间窗口内可复用成功作业。失败或部分失败作业不阻挡显式重新提交，重新提交创建新任务并关联前一任务 ID，保留旧任务历史。同一分析任务的后续提交以任务 ID 去重，不因 API 重启或 Worker 恢复而重复创建。

任务失败不自动触发紧密重试。管理员可以主动重试；连续提交同一种回填范围至少间隔 60 秒，活动作业仍直接复用。外部登录失效、风控与数据库权限错误分别提示，不通过重复扫码或放宽权限掩盖代码错误。

本次保持既有日历抓取算法与软对账策略，不自动对全部历史失败作业补跑。发布验收只新建一次近 7 天回填，不执行全年份历史重抓。

## 7. API 与页面兼容

保留 `/api/up-trends/refresh`、`/api/up-trends/progress` 的路径，以及 `task_id`、`total`、`current`、`current_up`、`eta_seconds`、`done` 字段。

- 首次提交保持成功返回；已有活动作业保持 409 + busy + task_id，前端接管同一作业。
- 查询返回持久化状态，新增 `status`、结构化错误/警告及关联日历 ID。分析结果通过现有数据库读路径加载，不将完整采集结果长期复制进任务 JSON。
- UP 配置检查响应增加 `active_task_id`；页面重新进入后接管活动任务，API 重启后仍可查询进度。
- `succeeded` 正常加载新数据；`partial` 展示已保存部分及后续失败提示；`failed` 保留上次可用数据并显示错误。不存在的任务、轮询网络异常和 Worker 不可用不能一直显示“启动中”。
- 日历进度仍使用现有查询接口，明确排队、运行、成功、部分失败、失败和登录状态。
- 不扩展访客权限，手动提交仍要求管理员。

## 8. 回归验证与验收

先添加能复现当前错误的失败测试，再最小实现并跑通：

1. API 点击刷新只创建数据库任务，不启动分析/日历线程，不发起采集网络请求。
2. 同时手动和定时提交、多个 API 进程提交时，只得到一个活动作业。
3. API 重启/换进程后进度仍存在；Worker 租约恢复后旧 token 不能写入进度或结果。
4. 核心 UP/快照任一写入失败，新批次全回滚，页面不误报成功；日历后续提交失败报告部分成功。
5. 日历网页提交不启动本地消费者；失败任务允许受控新建重试，历史保留。
6. PostgreSQL 真实角色测试验证 API 不能写采集结果表、Worker 可以；新迁移单 head、空库升级和 0002 增量升级成功。
7. 前端覆盖排队/成功/部分失败/失败、409 接管、刷新页面接管和轮询异常，并完成构建。

## 9. 发布保护与回退

先在独立工作区完成修复、测试和提交；不得把 SQLite 年代的本地主目录或旧部署副本整体覆盖到服务器。发布以核验后的目标提交和镜像身份进行。

维护前核验当前任务、代码和镜像身份，并记录数据库版本、观察名单数量、最新批次与日历任务基线。完成已在运行的采集，再停 API/Worker 写者，创建并验证 PostgreSQL 备份，执行新增迁移，然后启动新版本。公网入口继续关闭，管理仍走私有 SSH 入口。

新迁移只添加任务表及必要授权，不导入、删除或覆写既有数据。API/Worker 不能在启动时自动迁移。部署前需留存可用备份、旧镜像及提交。迁移前可直接退回旧镜像；迁移后不能直接承诺旧镜像恢复可用，因为旧版本 readiness 要求数据库版本与其 Alembic head 完全相等。迁移后验收失败时，停新服务并保留数据，优先前向修复；任何数据库恢复覆盖或 downgrade 都需另行确认，不能自动执行。

服务就绪不等于业务验收成功：必须实际核验网页提交、Worker 进度、UP/快照入库和日历终态，再报告修复完成。
